VLIR → Boole: Numeric Domain Classification

When the VLIR pipeline lowers a Rust/Verus program to Boole, every numeric value and every arithmetic operation is emitted in exactly one of three domains:

  • bv — a fixed-width bitvector (bv1, bv8, bv16, bv32, bv64). Wrapping arithmetic; overflow is a separate proof obligation.
  • int — a mathematical integer. Unbounded, never wraps.
  • nat — a non-negative integer. Unbounded above, with source-level preconditions (no division by zero, no negative subtraction) surfaced explicitly.

The domain is never chosen for convenience — it is chosen to be faithful to Verus semantics. The discriminator is simple to state:

The ground-truth rule. A Verus arithmetic op's result type decides its domain. An int or nat result means the operation is mathematical and never wraps; it is lowered in the int/nat domain. A uN/iN result (exec-mode, fixed width) is lowered in the bv domain, where overflow is handled as a separate obligation rather than by wrap-around in the model.

Variable promotion — the usize/isize story documented in the sibling docs/int-promotion.html — is one pass within this system. It moves selected source variables from the bv side onto the int side so that index reasoning stays in a single domain; the classification machinery described here is what decides, for every other value and operation, which domain applies.

1 · Spec-arithmetic result type drives the domain

Verus spec-mode arithmetic (+ - * / %) on finite-width operands is modeled as mathematical int/nat and never wraps. The mechanism is an explicit Clip marker that routes the operands through int-domain lowering with as_int widening.

The Binary arm of the parser captures the VLIR wrapper's result type via getTyp. For an .Arith op whose result type is .Int or .Nat, the parser wraps the binary node with .Unary (.Clip .Int/.Nat false). That Clip reaches Boole/Translate.lean, where arithRunsInInt detects spec-mode int/nat arithmetic and directs operands through prepScalarOperands at Typ.Int (widening each operand via the native as_int, the same coercion used in Sequence.select index handling). The domain is then set to .int, so numBinopEmit dispatches to applyBinaryOp, which emits the unbounded int + (faithfully summing without wrap). Exec-mode arithmetic keeps a finite-width uN result type, lacks the Clip, and stays in the bv domain where overflow is a separate obligation. 

-- Parser.lean Binary arm:
    match op, resultTy with
    | .Arith _ _, .Int => return .Unary (.Clip .Int false) binExp
    | .Arith _ _, .Nat => return .Unary (.Clip .Nat false) binExp

-- Boole/Translate arithRunsInInt:
    let arithRunsInInt :=
      match op with
      | .Arith _ _ =>
        match expectedKind? with
        | some .int | some .nat => true
    if arithRunsInInt then
      let (l, r) ← prepScalarOperands env bound Typ.Int lhs rhs
      match ← numBinopEmit .int op l r with

-- Sequence.select index coercion:
        let intIdx ← expToBoole env bound (some .Int) iArg

Example

Source spec fe1.limbs[i] + fe2.limbs[i] < bound — both operands are u64 limb values, but the add's result type is marked .Int in VLIR.

  • Parser emits: Clip .Int false (Binary (.Arith .Add …) (limbs[i] fe1) (limbs[i] fe2))
  • Boole routing: arithRunsInInt fires; both operands are translated at Typ.Int via prepScalarOperands, yielding Sequence.select(…) as_int on each side.
  • Domain dispatch: numBinopEmit .int fires, emitting the int + (unbounded add, no wrap) — the mathematical sum select(…) as_int + select(…) as_int < bound as_int.
  • Exec-mode contrast: a wrapping add such as wrapping_add keeps its uN result type (no Clip), stays in the bv domain, and uses bv + at width 64 (wrapping).
What the Clip does and does not do. The .Clip node performs no arithmetic itself — it is a marker that causes the inner expression to be evaluated in the int domain. The actual operand widening (as_int) happens while translating the operands at Typ.Int inside prepScalarOperands and the subsequent expToBoole calls. Dropping or mis-routing this marker would silently turn a never-wrapping spec sum into wrapping bv arithmetic.

2 · Three domains & numKindOfTyp? (Rule ①)

numKindOfTyp? is the single source of truth for numeric-domain classification. It folds Rule ①: integers whose width is outside the Boole-supported set {1, 8, 16, 32, 64} are faithfully modeled as mathematical integers, not bitvectors, because there is no native bv128 backend.

The function uses isSupportedBvWidth to test the width. For .UInt w and .SInt w, a supported width returns .bv w signed (the bitvector domain); otherwise it returns .int. Thus u128 and i128 fail the support check and are classified as .int. USize/ISize map to a bv at usizeBitWidth; bare .Int/.Nat map to .int/.nat; Decorated wrappers recurse on the payload. 

def numKindOfTyp? : Typ → Option NumKind
  | .Int => some .int
  | .Nat => some .nat
  | .UInt w => if isSupportedBvWidth w then some (.bv w false) else some .int
  | .SInt w => if isSupportedBvWidth w then some (.bv w true) else some .int
  | .USize => some (.bv usizeBitWidth false)
  | .ISize => some (.bv usizeBitWidth true)
  | .Decorated _ ty => numKindOfTyp? ty
  | _ => none

VerusLean/VLIR/Boole/Coercions.lean:81–98

Example

For u128, the pattern .UInt 128 matches the fourth clause; isSupportedBvWidth 128 returns false (128 ∉ {1,8,16,32,64}), so the function returns some .int rather than some (.bv 128 false). This causes field-mul products of two 64-bit limbs (which sum to ~128 bits) to be modeled as mathematical integers, where overflow is represented explicitly through side conditions rather than as automatic wrap-around.

Soundness side condition. Modeling u128/i128 as int drops wrap-around semantics; it is faithful only when the value provably never wraps. Verus discharges this as a side condition (e.g. the field-mul boundary lemmas ensure products of 64-bit limbs stay in range). The defining comment marks this explicitly — if a computation actually wraps, the mapping is unsound.

3 · Arithmetic footprint — source-domain classification

arithFootprint walks an arithmetic subtree and classifies each node as a mathematical integer or a bitvector; expHasMixedIntBvArith detects when both domains coexist in the same tree, which triggers int-space lowering with explicit bv→int casts.

arithFootprint recurses over the subtree, classifying each node via: Unbox (extracts the type from a boxed value), Clip (a Clip on Int/Nat yields hasMathInt), Const (a bv-typed literal yields hasBv; a fixed-width int literal yields hasMathInt), and leaf inference (variables/expressions delegated to inferNumKind). The merge operation OR-combines the two independent flags as the tree is traversed, and ArithFootprint.isMixed is true exactly when both flags are set. When mixed, expHasMixedIntBvArith signals the translation layer; arithRunsInInt becomes true, both operands are coerced to Int via prepScalarOperands, and the binary op runs in int-space. coerceNumeric then applies the explicit bv→int cast (bvToInt with width and signedness) to each bv operand. Pure-bv arithmetic stays in bv; pure-int stays in int; only mixed trees force int-space lowering and bv-operand casting. 

-- ArithFootprint classification and merge
private structure ArithFootprint where
  hasMathInt : Bool := false
  hasBv : Bool := false

private def ArithFootprint.merge (lhs rhs : ArithFootprint) : ArithFootprint :=
  { hasMathInt := lhs.hasMathInt || rhs.hasMathInt
    hasBv := lhs.hasBv || rhs.hasBv }

private def ArithFootprint.isMixed (f : ArithFootprint) : Bool :=
  f.hasMathInt && f.hasBv

VerusLean/VLIR/Boole/Inference.lean:440–508, 514–538 · VerusLean/VLIR/Boole/Translate.lean:949–960 · VerusLean/VLIR/Boole/Cast.lean:132–157

Example

u128_literal + bv64, where u128 is unsupported and modeled as int:

  • arithFootprint enters the Binary(.Arith, …) node and analyzes both children.
  • Left (u128_literal): the Const case hits with UInt 128 → hasMathInt := true.
  • Right (bv64 var): inferNumKind → some (.bv 64 unsigned) → hasBv := true.
  • merge → {hasMathInt: true, hasBv: true}; isMixed is true and expHasMixedIntBvArith detects it.
  • In Translate, arithRunsInInt becomes true; prepScalarOperands coerces both operands to Int; numBinopEmit runs + in the int domain; coerceNumeric applies .bvToInt 64 unsigned to the bv64 operand before the addition.

Literals of bare .Int/.Nat type do not contribute to the footprint unless they are explicitly fixed-width (UInt/SInt/USize/ISize) or have magnitude ≥ 2⁶⁴. This keeps them context-determined, so they do not force a mixed classification when paired with bv operands.

4 · Rule ③ — narrowing casts in int-modeled context wrap

A cast to a fixed-width integer type in the int domain applies wrapping formulas unless the inner source type syntactically fits the target. This prevents a real narrowing from being silently elided, which would change the meaning of the statement.

When lowering a Clip (numeric cast) to a fixed-width target in the int domain, clipWrapIntModeled first asks whether the inner's source type fits the target via fixedWidthInfoOfTyp and fitsFixedWidth (an unsigned cast to the same or larger width, or a signed cast to the same or larger width, always fits). If it fits, the inner passes through unchanged and the cast is elided. If it does not fit, wrapping is applied: for unsigned targets, inner mod 2^w; for signed targets, (inner + 2^(w-1)) mod 2^w − 2^(w-1) (Euclidean mod, implementing two's-complement reinterpretation). For expressions whose source type cannot be read syntactically (arithmetic trees, function calls returning nat/int) the fit check returns false and wrapping is applied conservatively, so a narrowing is never silently dropped (e.g. it would otherwise change companion lemmas such as lemma_u128_shr_is_div). 

private def clipWrapIntModeled (env : VarEnv) (bound : BoundEnv)
    (target : Nat × Bool) (e : Exp) (inner : BExpr) : BExpr :=
  let srcTy? := inferComparableTyp? env bound e <|>
    (match e with | .Const _ t => some t | _ => none)
  let fits := match srcTy?.bind fixedWidthInfoOfTyp with
    | some src => fitsFixedWidth src target
    | none => false
  if fits then inner
  else
    let (tw, tsigned) := target
    let full := Bld.intConst ((2 : Int) ^ tw)
    if tsigned then
      let half := Bld.intConst ((2 : Int) ^ (tw - 1))
      Bld.intSub (Bld.intMod (Bld.intAdd inner half) full) half
    else
      Bld.intMod inner full

VerusLean/VLIR/Boole/Translate.lean:609–634, 1043–1087 · VerusLean/VLIR/Boole/Coercions.lean:43–59

Examples

CastResultWhy
(x : u64) as u64 inner Source width 64 fits target width 64; fitsFixedWidth is true, cast elided.
(x : u128) as u64 inner mod 2^64 Source width 128 does not fit target width 64; unsigned wrap.
(x : i128) as i64 (inner + 2^63) mod 2^64 − 2^63 Source width 128 does not fit; signed two's-complement reinterpretation.
(x + y) as u64 inner mod 2^64 Arithmetic inner has no syntactically readable source type; srcTy? is none, fits false, wrap applied conservatively.
Scope and asymmetry. The rule applies only to fixed-width targets in the int domain (those that fixedWidthInfoOfTyp annotates). Width-less targets like as int or as nat bypass the wrapping gate. fitsFixedWidth is asymmetric: a signed value never fits an unsigned target, but an unsigned value can fit a signed target if the widths align (e.g. u63 fits i64, but u64 does not).

5 · Rule ④ — variable-amount shifts on int-modeled operands

Int-modeled bit-shifts with a non-constant amount lower to int division/multiplication via int_pow2, a prelude function carrying guard axioms for non-negative exponents.

Rule ④ fires when the value operand of a shift is modeled in the int domain (not bitvector). For a constant amount k, the shift rewrites directly to arithmetic: x >> k → x / 2^k and x << k → x * 2^k. For a non-constant amount e (a variable or expression), intShiftViaPow2 emits x div int_pow2(e) and x * int_pow2(e). int_pow2 is defined in the Nat.boole.st prelude as an uninterpreted function with three guarded axioms: int_pow2(0) = 1, int_pow2(e+1) = 2·int_pow2(e) for e ≥ 0, and 1 ≤ int_pow2(e) for e ≥ 0. The gate shiftValueIntModeled? checks the value operand's domain, so ordinary bitvector shifts are unaffected. 

/-- Extract a constant non-negative shift amount, peeling Box/Unbox/Clip
    wrappers.  Used by rule ④ to lower an int-modeled `x >> k` / `x << k` to
    int `x / 2^k` / `x * 2^k`. -/
private partial def constShiftAmount? : Exp → Option Nat
  | .Const (.Int k) _ => if k ≥ 0 then some k.toNat else none
  | .Unary (.Box _) e | .Unary (.Unbox _) e | .Unary (.Clip _ _) e =>
    constShiftAmount? e
  | _ => none

private partial def intShiftViaPow2 (env : VarEnv) (bound : BoundEnv)
    (expected? : Option Typ) (arithOp : ArithOp) (mode : Mode) (lhs rhs : Exp) :
    BuildM BExpr := do
  let (l, r) ← prepScalarOperands env bound Typ.Int lhs rhs
  let powIdx ← resolveFreeVar "int_pow2"
  let powR := Bld.app (Bld.fvar powIdx) r
  match ← numBinopEmit .int (.Arith arithOp mode) l powR with
  | some result => coerceNumeric (some .int) (expected?.bind numKindOfTyp?) result

Soundness window. int_pow2 is uninterpreted with guarded axioms defined only for e ≥ 0; negative exponents are unconstrained. The lowering is sound only for non-negative, in-range shift amounts — exactly matching the source language. The gate shiftValueIntModeled? deliberately inspects the value operand's domain, not the shift amount, so ordinary bitvector shifts keep their native bv semantics.

6 · Exec overflow via HasType ranges

Verus materializes arithmetic overflow obligations as assert HasType(τ, e) (paired with assume HasType(τ, e)) around clipped assignments. The translator lowers numeric HasType to a range predicate; non-numeric HasType is dropped as a typing tautology.

hasTypeRangeCond converts a numeric HasType into a range by extracting the type's bit-width or nat classification: for unsigned width w, 0 ≤ e ≤ 2^w − 1; for signed width w, −2^(w−1) ≤ e ≤ 2^(w−1) − 1; for nat, 0 ≤ e (no upper bound). The result compiles to a conjunction of integer comparisons. Asserts emit the range obligation directly; assumes re-inject the checked-range fact to the solver. Non-numeric types (bool, datatypes, sequences, width-less int) return none and are dropped — the Boole type system enforces their membership by typing alone. This is what prevents silent discharge of overflow obligations under int-model wrap-around. 

private def hasTypeRangeCond (env : VarEnv) (t : Typ) (inner : Exp) :
    BuildM (Option BExpr) := do
  let range? : Option (Option Int × Option Int) :=
    match fixedWidthInfoOfTyp t with
    | some (w, false) => some (some 0, some ((2 : Int) ^ w - 1))
    | some (w, true)  => some (some (-((2 : Int) ^ (w - 1))), some ((2 : Int) ^ (w - 1) - 1))
    | none => if numKindOfTyp? t == some .nat then some (some 0, none) else none
  match range? with
  | none => pure none
  | some (lo?, hi?) =>
    let x ← expToBooleFlat env (some .Int) inner
    let conds := (lo?.map (fun lo => Bld.intLe (Bld.intConst lo) x)).toList ++
      (hi?.map (fun hi => Bld.intLe x (Bld.intConst hi))).toList
    match conds with
    | [c] => pure (some c)
    | [c1, c2] => pure (some (Bld.boolAnd c1 c2))
    | _ => pure none

-- In assertion handling:
| .Unary (.HasType t) inner =>
  match ← hasTypeRangeCond env t inner with
  | some c => return [assertStmt "" c]
  | none => return []

Examples

  • HasType(u8, x) in an assert → range (0, 255) compiles to 0 ≤ x ≤ 255 as the overflow condition.
  • HasType(i32, y) → −2147483648 ≤ y ≤ 2147483647.
  • HasType(int, z) or HasType(bool, b) → returns none; the assert is dropped.
  • In assumes, the same range predicate reinstates the post-check invariant, so the int model's unbounded arithmetic remains constrained by the verified bitvector width.
Classification dependency. The mechanism relies on fixedWidthInfoOfTyp and numKindOfTyp? to classify types. Unsupported widths (e.g. an unhandled u128) fall through to none and are silently dropped, and the int-model translation of the inner expression must itself be faithful — if expToBooleFlat env (some .Int) inner does not preserve the arithmetic, the range obligation can be under-constrained.

7 · Nat-native lowering — the third domain

Arithmetic and comparison in nat-space emit prelude functions (nat.add, nat.sub, nat.mul, nat.div, nat.mod, nat.le, nat.lt, nat.ge, nat.gt) that carry the source-level preconditions directly, rather than hiding them behind int round-trips.

When the expected type is Nat (propagated from .Unary (.Clip .Nat _)), or operands are inferred nat-kinded, or it is a EuclideanMod with nat operands, the translator routes to nat-native prelude functions. natCmpFn maps inequalities to nat.le/nat.lt/nat.ge/nat.gt; natArithFn? maps Add→nat.add, Sub→nat.sub, Mul→nat.mul, EuclideanDiv→nat.div, EuclideanMod→nat.mod. numBinopEmit dispatches on the .nat domain by resolving the prelude name and applying it. Operands are translated at Nat type, so preconditions surface directly: nat.sub requires nat.toInt(b) ≤ nat.toInt(a); nat.div and nat.mod require nat.toInt(b) ≠ 0 — exactly the obligations Verus discharges at the source. 

-- natArithFn? (Translate.lean):
def natArithFn? : BinaryOp → Option String
  | .Arith .Add _          => some "nat.add"
  | .Arith .Sub _          => some "nat.sub"
  | .Arith .Mul _          => some "nat.mul"
  | .Arith .EuclideanDiv _ => some "nat.div"
  | .Arith .EuclideanMod _ => some "nat.mod"
  | _                      => none

-- Prelude function signatures (Nat.boole.st):
function nat.add (a : nat, b : nat) : nat { nat.fromInt(nat.toInt(a) + nat.toInt(b)) }
function nat.sub (a : nat, b : nat) : nat
  requires nat.toInt(b) <= nat.toInt(a);
{ nat.fromInt(nat.toInt(a) - nat.toInt(b)) }
function nat.div (a : nat, b : nat) : nat
  requires nat.toInt(b) != 0;
{ nat.fromInt(nat.toInt(a) div nat.toInt(b)) }
function nat.mod (a : nat, b : nat) : nat
  requires nat.toInt(b) != 0;
{ nat.fromInt(nat.toInt(a) mod nat.toInt(b)) }

VerusLean/VLIR/Boole/Translate.lean:481–947 · prelude/Nat.boole.st:30–54

Example

Translating a Verus spec with nat arithmetic — e.g. n − m where both are nat-typed, or x % p where x and p are operand-inferred nat — emits nat.sub or nat.mod with the precondition appearing in the Boole output. For instance, n − m emits nat.sub(n, m) with precondition nat.toInt(m) ≤ nat.toInt(n), faithfully surfacing the Verus source obligation rather than implicitly lowering to nat.fromInt(nat.toInt(n) − nat.toInt(m)).

Operand-driven exception for mod. EuclideanMod (nat.mod) additionally fires on operand types when both operands are inferred nat, not just on the expected type. This is restricted to mod, to preserve expected-driven firing for nat.sub and nat.div.

8 · Emission & comparison-domain selection

Three pieces cooperate at emission time: numBinopEmit dispatches (domain, op) to domain-specific operators; inferComparisonNumKind joins arithmetic-tree operands to recover a domain when the leaves alone are opaque; and comparisonPrelude reconciles the two sides of a comparison onto a single domain before emission.

numBinopEmit accepts a NumDomain and a BinaryOp and emits the matching operator: for .int it applies the standard operators; for .nat it resolves prelude names via natCmpFn/natArithFn?; for .bv it maps to signed/unsigned comparison opcodes (SLe/ULe/SLt/ULt …) and width-tracked arithmetic/bitwise operators. inferComparisonNumKind solves the gap that inferNumKind has no .Binary case, so a tree like a % p initially infers none; on a .Binary(.Arith _ _) node it recursively joins both operands via joinArithNumKind, making the tree's kind visible so both comparison sides pick a consistent domain. comparisonPrelude orchestrates the reconciliation: it collects bitvector shape and numeric kind for both operands, calls chooseBitArgTyForCmp to prefer bv space only if both operands are naturally bv-shaped or constants fit; if bv is rejected and either side carries a numeric signal it falls back to int space, translating both at some Typ.Int and post-coercing via coerceNumeric; otherwise it coerces both sides to the target bv shape via coerceBvBv, so both operands share a domain before emission. 

-- numBinopEmit dispatcher:
def numBinopEmit (domain : NumDomain) (op : BinaryOp) (l r : BExpr) :
    BuildM (Option BExpr) := do
  match domain with
  | .int => pure (applyBinaryOp op l r)

-- inferComparisonNumKind joins an arithmetic tree:
match e with
| .Binary (.Arith _ _) l r =>
  joinArithNumKind (inferComparisonNumKind env bound l)
    (inferComparisonNumKind env bound r)

-- comparisonPrelude int fallback:
if fallbackToInt then
  let l0 ← expToBoole env bound (some Typ.Int) lhs
  let r0 ← expToBoole env bound (some Typ.Int) rhs
  let l ← if exprHonorsExpectedInt lhs then pure l0
          else coerceNumeric lhsNum? (some .int) l0

VerusLean/VLIR/Boole/Translate.lean:553–598, 722–767 · VerusLean/VLIR/Boole/Inference.lean:551–569

Example

Comparing (n : nat) + 1 (an arithmetic tree) against a bitvector:

  1. inferComparisonNumKind recursively joins the operands of the .Binary node, discovers both are nat-kinded, and infers .nat for the tree.
  2. comparisonPrelude collects this signal; chooseBitArgTyForCmp rejects bv space because the arithmetic side is non-constant; fallbackToInt triggers because lhsNum?/rhsNum? == some .nat.
  3. Both sides translate at some Typ.Int; the bv side coerces through coerceNumeric to match .int.
  4. numBinopEmit receives domain = .int and emits the standard applyBinaryOp. Both sides are reconciled to the int domain before the comparison.

The reconciliation relies on exprHonorsExpectedInt to avoid double-wrapping: arithmetic expressions that already honor the expected type are not post-coerced. Likewise, bv coercion assumes coerceBvBv infers widths correctly when both sides are already bv.
