VLIR → Boole: usize/isize Int Promotion

This document explains how Rust usize and isize values are encoded when the VLIR pipeline lowers them to Boole. There are two layers, and they follow different rules:

  1. Sequence-index slots are always int-typed at the call site, regardless of the source variable's declared type.
  2. The variable's declared type is decided by a per-procedure pass called IntPromotion, which only retypes a local to Int when it has sequence-index/length evidence and no bv-forcing use.

Both layers exist because they have different cost/risk profiles. Layer 1 does not retarget the source variable — at worst it inserts an explicit cast helper at the Sequence boundary. Layer 2 is more invasive — it changes the variable's lowered contract, so it has to be conservative.

Scope. This document covers only the usize/isize variable-promotion story. It is one optimization layer within a larger numeric-domain classification system that decides, for every value and operation, whether it is lowered in the bv, int, or nat domain — including the rule that spec-mode arithmetic with an int/nat result type is mathematical (never wraps), the unsupported-width (u128) modeling, narrowing-cast wrap, variable-amount shifts, and exec overflow checks. That machinery is documented in the sibling docs/numeric-domains.html; variable promotion runs as one pass within it.

Layer 1: Sequence-index slots are always int

Strata's Sequence.select, Sequence.update, Sequence.subrange, etc. are indexed by mathematical int. So the translator asks expToBoole to produce an int-typed expression at every index slot, by passing expected = some .Int directly (rather than translating bv-typed first and then post-coercing).

The four index-lowering arms in VerusLean/VLIR/Boole/Translate.lean:

  • isArrayIndexGetName — Rust [T; N] read
  • isSliceIndexGetName — Rust &[T] read
  • isVecIndexSpecName / isVecIndexExecName — Vec<T> read
  • isIndexSetName — container[i] = v write side (Std_specs_Core_index_set)

All four pass expected = some .Int to the index translator. The resulting expression at the index slot is always int-typed, but the way that expression is built depends on the source shape:

Source shape at the index positionGenerated BooleWhy
0_usize, 5_u64, … (bv-typed literal) 0, 5 The Const arm respects expected = some .Int and emits a literal intConst.
k where k was promoted by IntPromotion (env says int) k The variable's declared type is already int; no coercion needed.
k where k stays bv (env says bv64) k as_int coerceNumeric applies Strata's native, interpreted as_int cast.
i + 1 on a promoted i i + 1 Pure int arithmetic flows through; no cast.
i + 1 on an un-promoted bv i (i + bv{64}(1)) as_int Arithmetic stays bv, then the result is cast to int at the slot via the native as_int.
Faithfulness vs. solver visibility. The as_int cast makes the required domain crossing explicit without changing the source variable's lowered type. Unlike the older bv64_to_int_u (an uninterpreted function), as_int is Strata's native, interpreted cast (PR #1217 / pr/casts-boole): cvc5's bitvector theory reasons about it directly, so 0 ≤ k < len(s) on the bv side can be related to 0 ≤ k as_int < Sequence.length(s) on the int side without explicit axioms. The cast is therefore no longer opaque. Layer 2 still removes even these casts — by getting the variable itself onto the int side — which avoids the cast entirely and keeps the loop's index reasoning in one domain.

Layer 2: IntPromotion (variable declaration retype)

The pass lives in VerusLean/VLIR/Boole/IntPromotion.lean and runs once per procedure. It returns a HashSet String of names whose declared type should be rewritten from USize/ISize to Int. The translator then rewrites every matching LocalDeclInfo.ty and every Assign.lhsTy in the body before the rest of the lowering runs.

Candidate set

A name is eligible for consideration iff it is:

  • A USize- or ISize-typed local in f.locals (modulo Decorated wrappers like Ref, MutRef, Box, Ghost, Tracked).
  • A USize- or ISize-typed for-loop binder discovered through recoverForLoop?.

Never candidates:

  • Procedure inputs and &mut outputs (they cross call boundaries).
  • Struct/enum fields (they're part of an externally-visible datatype contract).
  • Fixed-width UInt w / SInt w at any width, including 64-bit — we only promote source usize/isize, not arbitrary bitvector locals that happen to share the same target width.

Promotion rule

A candidate k is promoted iff all three conditions hold:

1 · At least one qualifying use

Use siteExamples
Index slot of an indexer call Vec_index_exec(v, k), Vec_index_spec(v, k), Array_array_index_get(a, k), Slice_slice_index_get(s, k), Std_specs_Core_index_set(c, k, value) (the index arg only).
Index / range slot of a Seq_* op Seq_index(s, k), Seq_update(s, k, v), Seq_take(s, k), Seq_skip(s, k), Seq_subrange(s, lo, hi), Seq_lib_remove(s, k).
Comparison against a length call k < blocks.len(), k == s.view().len(), k <= Sequence.length(s).
For-loop bound is a length call for k in 0..blocks.len() qualifies the binder k.

2 · No rejecting use

Use siteExamples
Operand of a bitwise op k & 0xff, k | mask, k ^ x, k << 3, k >> 1, !k
Explicit bv↔bv or bv↔int cast any bv*_to_* / int_to_bv*_* wrapping k
Argument to an opaque Stm.Call some_user_fn(k) — we can't see the callee's parameter type, so we conservatively reject. Exception: the index slot of Std_specs_Core_index_set is recognized specially.
Value slot of a value-storing Seq_* op The second arg of Seq_push(s, k), Seq_lib_contains(s, k) — k is being stored or matched, not used as an index.
Field of a struct/enum/tuple ctor MyStruct { count: k, .. }, (k, other), MyEnum::Variant { idx: k }.
RHS assigned into a non-candidate bv-typed target some_bv64_var := k — the target forces the RHS to remain bv-compatible.
Inside an AssertBitVector block assert by bit_vector { k > 0 && k < N } — bv-only by definition.
Operand of a CallLambda The lambda body and all of its arguments are visited with reject context — the lambda is opaque, like a user-procedure call.

3 · Fixpoint closure on assignment chains

For every k := rhs seen during the walk, edges are recorded from every candidate j₁, …, jₙ referenced in rhs to k. Then propagateOnce is iterated until stable:

  • Forward: if any jᵢ is rejected, reject k (a rejected RHS taints the LHS).
  • Backward: if k is rejected, reject every jᵢ (a rejected LHS means the RHS was used in a bv-forced context).

Both directions matter. Forward propagation alone catches "j rejected → k := j → reject k". Without backward propagation, a counter k that flows into a bv-forced context can stay promoted while a sibling j that fed k also stays promoted, creating inconsistent emitted casts around the assignment chain. Backward propagation closes that asymmetry.

Transparent wrappers

The classifier sees through three Verus-inserted scaffolding wrappers and recurses on the payload with the same surrounding context:

  • Unary[Box _] — Verus type-erasure
  • Unary[Unbox _] — inverse erasure
  • Unary[Clip _ _] — Verus overflow-check artifact

The same transparency is applied in expToBoole's Box/Clip arms when expected? = some Int, so the wrappers don't drop the int context and don't generate avoidable cast round-trips.

Binder shadowing

The walker tracks a shadowed : HashSet String set containing every Bind binder currently in scope (from Let, Quant, Lambda, Choose). A Var k reference inside such a binder is attributed to the inner binder, not the outer candidate. So if a procedure has 

let mut k: usize = 0;
…
assert(forall|k: int| k >= 0);    // inner k shadows outer

the inner k in the quantifier body doesn't count toward the outer candidate's use classification.

What is deliberately not promoted

These cases are intentional design choices, not gaps:

  • Variables used only in pure int arithmetic (no sequence touch-point). Per the working rule, a candidate must have at least one sequence-index or length-comparison use to be promoted. A pure counter while k < N { k += 1 } where N is just a literal stays bv. The reasoning: changing the declared type of a variable that has no sequence interaction is churn without benefit.
  • Variables passed to user-procedure calls — we can't see the callee's parameter types, so promoting would risk a type mismatch at the call boundary. Future work: a per-callee whitelist for known-int-typed parameters.
  • Variables stored into struct/enum/tuple fields — the consuming side likely expects the source type.
  • Procedure inputs and &mut outputs — these are part of the function's external contract and must preserve their declared type.
